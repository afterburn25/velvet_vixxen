## What changes

Payment operations are saved before a provider call. Confirmed results are bound to the installation, provider, merchant account, environment, order, amount, currency and original operation. Refunds also bind the original financial reference. Duplicate or conflicting references are rejected; an unavailable result stays pending, unknown or held. Recovery queries the original operation and applies confirmed local changes without sending another charge or refund.

Order status, transaction history, access, coupons, stock and journal state commit together on the file and SQL backends. Receipts, attribution and add-on notifications are separate durable follow-ups. Completed work stays completed; a proven temporary failure can be retried, while an interrupted external effect remains held when delivery may already have happened. Provider callbacks run outside financial transactions.

Owners open **Admin → Commerce → Payment recovery**, also linked from Orders and Payment Settings. The workspace offers a bounded list, exact order filter, record review, **Check payment outcome** and **Run eligible order follow-ups**. It excludes customer contact details, payment tokens, merchant bindings and raw provider payloads. Reads do not query providers, run add-ons or send mail. The interface works on desktop and phone, with keyboard controls and without JavaScript.

Every protected operation checks the current active owner, recent authentication, method, CSRF and the saved record revision as applicable. Refund authority is repeated after lock waits and at protected boundaries. If permission expires after provider acceptance may have occurred, the operation stays recoverable through lookup. A first charge also requires a currently active, verified member whose account remains open, including for zero-value orders.

Account closure and first-charge dispatch use the existing commerce mutex in the same order. A completed freeze prevents a waiting first charge. A charge that starts first makes closure wait and recheck the approved inventory and current owner. Changed records require fresh review. Entry from an unrelated SQL transaction or nested member/file mutation is refused to prevent inverted lock order. Accepted financial settlement and refunds remain possible after closure without restoring access or contact.

Migration `202610220018_payment_journal.php` adds the payment journals. Fresh and complete Upgrade packages retain the approved runtime roots, existing customer state and historical installer behavior. The separate unfinished-installer repair remains byte-identical at **0.8.1 / repair Build 20261020.3**.
