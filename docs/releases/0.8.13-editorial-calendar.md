## Owner workflow: review saved dates

Open **Marketing & Publishing → Calendar** in the owner admin. Choose **Month** and **Content type**, then **Show calendar**, or use **Previous**, **This month** and **Next**. The selected type is retained when moving between months. Select a dated day to jump to that day's agenda, then use the entry's editor link to make a deliberate change in the existing editor.

The calendar and agenda display the configured site timezone. Agenda timestamps include seconds and the timezone abbreviation, distinguishing the two instants in a repeated daylight-saving hour. January 1970 through December 9998 are supported. The **Without a date or needing review** section includes undated drafts and malformed/conflicting dates regardless of the selected month. A month without dated entries has a useful empty state and working navigation.

| Content type | Saved dates shown | Meaning and next action |
| --- | --- | --- |
| Posts | Publication and optional expiration | Open Posts to edit dates; current publication and audience rules still govern public visibility. |
| Banners | Start and end | Open the saved banner; enabled state and its existing window still apply. |
| Landing pages | Start and end | Open the saved landing page in Campaigns; existing access and window rules remain. |
| Galleries and videos | Saved publication and scheduled dates | Open the relevant media editor. Existing media scheduling uses its existing runner. |
| Music | Album, track and playlist publication/scheduled dates | Open the exact saved album, track or playlist; native editor links work without JavaScript. |
| Email campaigns | Saved scheduled dates | Current draft, paused and queued states remain distinct. A displayed date does not establish that mail was sent. |
| Hero and Visual Footer | Retained publication timestamps and undated drafts | Open Visual Composer. The newest 20 retained publications per section are represented; automatic scene activation and expiration remain separate work. |

Each state describes the saved item **now**. The calendar does not reconstruct its historical state on a past day. Separate publication and expiration entries may refer to the same post. Viewing a date neither publishes nor reschedules anything; editing remains in the existing editors. The [owner calendar guide](../EDITORIAL_CALENDAR.md) covers these distinctions.

## Owner workflow: optional post expiration and history

1. Open **Marketing & Publishing → Posts** and edit the post.
2. Enter **Expires at (optional)** in the site timezone, or leave it blank for no expiration. When a publication date is present, expiration must be later.
3. Save the post. A saved draft stays a draft; use the ordinary publication controls deliberately when it is ready.
4. Review the date in Calendar and use the private saved-owner preview where appropriate.

Public eligibility uses an inclusive publication bound and exclusive expiration bound: **publication ≤ request time < expiration**, whenever those bounds exist. At the exact expiration instant, the item displays **Expired** and leaves public listings, direct public pages and related-post suggestions. Existing Public/Members/Selected tiers rules still apply before expiration. Expiration does not delete the saved post or rewrite its saved `published` status. Visibility is evaluated when a request is handled, so this transition needs no calendar visit or publication worker.

The active owner can still inspect an expired saved post through the private preview and history workflow. Impossible dates, malformed input, skipped daylight-saving times and equal/reversed bounds are refused. Rejected edits retain the attempted values for correction and do not change the saved publication. An unchanged displayed time preserves the saved instant and offset, including a repeated-hour offset. An older form omitting the expiration field preserves the existing value or legacy absence; deliberately clearing it removes the expiration bound.

History captures expiration together with the rest of the post. Reviewing a version from before expiration existed shows **No expiry**. Restoring that historical version removes a newer expiration rather than inheriting it, and **every restore leaves the post Draft**. Review the restored content, audience and dates before publishing again. Current saved ownership, CSRF and revision checks protect edits and restores on both file and MySQL storage.

## Read-only and authorization boundaries

The owner-only calendar sends private, non-cacheable responses and reads saved calendar metadata. It bypasses add-on startup and initializing Marketing storage access. Its read path does not create missing publishing files or guards, invoke publication/queue workers, write analytics events, send mail or copy post bodies, campaign recipients and private media paths into calendar cards. Ordinary admin session/navigation preferences remain normal session state.

Current saved ownership is checked before reads and again before output. Actual MySQL acceptance held the authoritative `marketing_storage_records` SELECT, revoked ownership while it waited, released the lock and observed a **403** with unchanged saved records. Missing/unavailable SQL authority is held without a silent file fallback. Invalid filter shapes are refused; malformed calendar tab aliases fall back safely without exposing the calendar or producing a server error. Marketing ownership checks also precede CSRF error output, covering stale-owner requests with valid and invalid CSRF tokens.

No new database migration is added. The existing explicit owner-reviewed move from file storage to MySQL remains the activation workflow; opening Calendar does not perform that move.
