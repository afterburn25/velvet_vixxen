## Reproduced defect

Composer already drew each device layout at a fixed design aspect ratio: 1440, 900 or 390 design pixels wide, divided by its saved section height. The public renderer instead applied that saved height as a fixed CSS `min-height` at every actual browser width. A percentage-width photo therefore grew with a wider browser while its scene's height stayed fixed. The lower part could disappear outside the clipped scene even though it remained visible in Composer. The different aspect ratio also changed background `cover` cropping.

The negative control rebuilt and served the original customer Fresh package from `c07c02bd0b6957cba4e0c9d6722765e262e37157`, without a development routing fallback. Its SHA-256 is **`7251336a4aee0acdf8ecf8167d77525e5b273992113ebe3451affe32e1862df3`**, matching the delivered 0.8.9 package. The browser used the actual authenticated owner scene API and Full Page Preview with a transparent geometric photo and grid background.

| Original-package observation | Measured result |
| --- | --- |
| Composer desktop frame | 800 × 422.21875 displayed pixels, representing the saved 1440 × 760 design canvas. |
| Public owner preview at 1680px wide | 1680 × 760 pixels. |
| Required height/width ratio | `760 / 1440 = 0.52777778`. |
| Actual public height/width ratio | `760 / 1680 = 0.45238095`; the focused assertion failed. |
| Photo height as a fraction of the frame | Approximately 0.79994 in Composer, versus 0.93331 on the public page. |
| Photo's normalized lower edge | Approximately 0.99896 in Composer, versus 1.06565 publicly; the public scene clipped the lower portion. |

These are observed original-package measurements. The separate 1920px example follows the same projection formula: a 760px design height requires a 1013.33px public height at that width to preserve the authored composition.

## Corrected rendering contract

A shared geometry helper defines the device widths, breakpoints and bounded design heights. Composer fits that design canvas into its editing panel. The public Hero and Visual Footer now render the complete design canvas at its saved size and project it uniformly into the actual available section width. The scene's displayed height is:

`displayed height = saved design height × actual section width / design width`

| Public viewport width | Device layout | Design width | Default Hero height | Default Footer height |
| --- | --- | ---: | ---: | ---: |
| More than 1120px | Desktop | 1440px | 760px | 420px |
| More than 760px, through 1120px | Tablet | 900px | 900px | 520px |
| Through 760px | Mobile | 390px | 860px | 620px |

Existing owner heights remain supported between 280 and 1800 design pixels. At the representative design widths, valid existing scenes retain their prior geometry. Between those widths, background fitting and focal positions, photo centers and sizes, intentional edge crops, rotations/flips, live content, standalone buttons, border/radius/font sizes and pixel effects scale together. Viewport changes select the appropriate existing device layout; a resize observer also updates projection when the available section width changes.

Public section padding and minimum-height rules cannot enlarge or shrink the composed frame. The following paper section retains its torn edge but no longer overlaps the Hero's last visible pixels. The sticky public navigation remains outside the scene. Footer decoration and its existing live content remain part of the uniformly scaled canvas.

No scene migration or owner resave is required. Rendering reads existing drafts/publications without changing saved coordinates, source images, device layouts, content groups, unrelated fields or history. Save Draft, Full Page Preview, Publish and restoration continue to use the existing owner API and persistence. The fix adds no route, database migration or asset-generation workflow.

The pink **Live text + buttons** box remains a positioning guide. **Full Page Preview** shows the actual headline, copy and controls in context. The focused regression separately compares the guide's rectangle with the live content rectangle and compares actual public text/button wrapping and clipping across widths within the same device layout. It does not claim that the guide contains the full live copy.

## Compact, readable site footer

The owner also requested larger footer text, a blue Cajun Web Pro link opening in a new tab, and less footer height. Both the homepage and shared public legal footer include **Website designed & developed by Cajun Web Pro LLC**, with the canonical `https://cajunwebpro.com/` destination, `target="_blank"` and `rel="noopener noreferrer"`.

The credit is blue (`#73baff`) and underlined, with a lighter hover/focus color and a visible keyboard outline. Navigation, legal links and the credit use 16px text. The brand grows from 2.25rem to 2.6rem, its subtitle from .63rem to .8rem, and the signature from 2.1rem to 2.4rem on larger screens or from 1.7rem to 2rem on mobile.

Observed bottom-footer heights are 110.328px at 760–1440px, 132.719px at 390px and 193.656px at 320px for both renderers and installation paths. The narrowest size uses natural wrapping of enlarged text and the credit; there is no empty height reservation. Desktop height is below the former 118px minimum.

The footer removes the previous 118px minimum height, reduces vertical padding to 8px and row gaps to 4px, and wraps its content in responsive columns. It grows only as its content requires. Existing navigation visibility through the 1120px breakpoint and legal-link visibility through 760px are preserved. This bottom-footer typography does not change the Visual Footer scene's saved canvas, copy or image positioning.

The extended actual-package browser acceptance checks both homepage/common renderers at 320, 390, 760, 900, 1121 and 1440px in root and nested installations: **24 footer layouts**, plus **eight real new-tab clicks** with the external destination fulfilled locally. It measures text size, blue underlined styling, content containment, nonoverlap and intrinsic height; the 1440px footer must be shorter than the former 118px minimum. It verifies that the original page stays open and the new tab has no opener reference. These checks are additional to the retained 52 scene comparisons, not a replacement for them. Eight additional observations use actual server-generated empty catalogues to check hidden players and zero reserved body padding. The complete focused run saves 34 PNGs: 26 scene captures and eight legal-footer captures.

The first footer freeze reproduced a real click obstruction: the fixed audio player covered the credit on the homepage, which lacked the common pages' player clearance. That failed package was not accepted or delivered. The corrected player code tracks its rendered height and hidden state, reserving height + 8px below page content only while visible. Footer height itself remains content-driven. Real pointer clicks and visible-player clearance are required at the document bottom; the test does not hide the player or force a click through it.
