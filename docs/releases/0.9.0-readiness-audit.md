## Payment source gaps

### 1. Actual adapter and live checkout — provider selection required

[app/Payments/PaymentProviderRegistry.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Payments/PaymentProviderRegistry.php) lines 13–28 registers only `SandboxPaymentProvider`. Its charge/refund methods fabricate results and IDs ([app/Payments/SandboxPaymentProvider.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Payments/SandboxPaymentProvider.php), 25–74). Public checkout still renders test-card, Approve/Decline/Processing and test-confirmation controls ([public/routes/checkout/index.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/public/routes/checkout/index.php), 68–80, 102–123).

The selected integration needs its real hosted/tokenized checkout, authenticated transport, test/live account separation, signed callbacks, recurring agreements, refunds, chargebacks and reconciliation; registry/configuration/UI changes; protocol fixtures; and actual merchant testing. [SECURITY.md](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/SECURITY.md) § Payment boundary (30–32) expressly requires approved hosted/tokenized collection.

**Required owner choices:** approved processor and merchant account for the actual site/business model; supported one-time PPV/rental/merchandise and recurring memberships; merchant region/currencies; trial, interval, cancellation/refund and grace rules; test/live integration method and secure account/webhook configuration; real HTTPS origins and specifically authorized merchant test transactions.

### 2. Recoverable operations and ambiguous outcomes — shared preparation possible

`checkoutLocked` marks every provider exception failed and releases stock. `refundOrderLocked` calls the provider before recording its result. Webhook effects precede the replay journal. The commerce lock serializes execution but is not an atomic transaction over all writes or external effects.

Before live enablement, introduce stable operation identities, explicit unknown/confirmed/failed states, reconciliation without blind recharging/refunding, and durable authenticated events with resumable effects. Offline fakes can cover accepted-then-timeout, interruption, concurrent retries and partial-refund recovery.

Evidence: [app/Core/CommerceService.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Core/CommerceService.php) §§ checkoutLocked / refundOrderLocked / handleWebhookLocked / applyExternalRefund (187–224, 318–355, 554–617, 631–667); [app/Core/MerchandiseStoreTrait.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Core/MerchandiseStoreTrait.php) § withCommerceLock (13–44); [app/Core/CommerceStoreTrait.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Core/CommerceStoreTrait.php) §§ transaction/event persistence (338–359).

### 3. Normalized payment results/events — shared preparation possible

The interface returns generic arrays. The reducer resolves `order_number` and applies local amounts/currency without a required normalized binding to provider, merchant/environment, remote transaction and expected amount/currency. The HTTP entry has an unbounded body read and one sandbox signature header.

Define bounded, allowlisted results/events and validate identities, money, statuses and transitions before effects; persist only necessary safe metadata. Reject malformed/conflicting/cross-order or cross-provider input. The chosen adapter must supply its actual signature/header/freshness protocol.

Evidence: [app/Payments/PaymentProviderInterface.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Payments/PaymentProviderInterface.php) (14–30), [public/routes/api/payment-webhook.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/public/routes/api/payment-webhook.php) (3–7), [app/Core/CommerceService.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Core/CommerceService.php) (531–617). Existing [tests/Security/payment_webhook.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/tests/Security/payment_webhook.php) (19–61) tests the sandbox HMAC contract.

### 4. Recurring lifecycle — shared boundaries now; actual calls depend on provider

Plan fulfillment creates a random `sub_` identifier and local periods. Cancel/resume updates local records only; non-sandbox renewal defers. The interface has no agreement/cancel/resume operations, and the webhook reducer handles only order paid/refunded/chargeback.

Add provider capabilities and lifecycle command/event contracts, real remote agreement identifiers and authoritative periods. Handle confirmed renewal, failure and cancellation, including trials/free initial checkout. Actual API calls and event mappings require the chosen processor. Privacy closure must continue requiring external billing review until cancellation is actually confirmed.

Evidence: [app/Core/CommerceService.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Core/CommerceService.php) (198–202, 259–272, 371–433, 565–613); [app/Payments/PaymentProviderInterface.php](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Payments/PaymentProviderInterface.php) (6–30); [app/Docs/MEMBER_PRIVACY.md](https://github.com/afterburn25/velvet_vixxen/blob/d3720e2ac3e8d948ff5834900fdaa1dd91a04234/app/Docs/MEMBER_PRIVACY.md) § Owner review and retention (70–97).
