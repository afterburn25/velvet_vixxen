## Owner behavior

The current active owner opens **Site & Design → Menus** and chooses **Header** or **Footer**. Each location has independent saved items and an independent edit revision. Selecting an item's name opens its fields: label, destination, opening behavior, parent and visibility. Add item creates a top-level link; Add submenu creates a child. Up and down move an item among its siblings. Changing Parent item moves an existing branch, with choices that would create a cycle or exceed the supported depth excluded. Removing a parent confirms that its children will be removed too. The owner reviews the draft and chooses Save menu to publish it.

Each location supports **50 total items**, **three levels**, labels of **1–80 UTF-8 characters**, and destinations of at most **2048 bytes**. Supported destinations include paths on this installation, page-local fragments, and complete `http://` or `https://` addresses. `/` means the installation homepage, including a nested installation. A destination-free parent must contain children and use Same tab; it acts as a submenu heading. Hiding a parent hides its entire branch. A heading with no visible children is omitted from public output.

New tab uses a native separate-tab link. New window requests a separate browser window from a direct visitor activation and retains a native new-tab fallback. Browser preferences and popup rules may choose a tab or block a window request. Both options use opener isolation; modified clicks keep normal browser behavior. This release does not promise control over a visitor's operating-system window placement.

The client uses plain text DOM assignment for labels and keeps editing within a bounded nested list. Save is disabled until the editor has safely parsed the server payload. The server retains attempted JSON and its **original submitted revision** after validation failure, an expired form token, or a stale edit. Retained drafts are marked unsaved, and leaving or explicitly reloading requires the editor's discard confirmation. A stale form never silently adopts a newer revision. Reload the saved menu before applying changes on top of another tab's save or reset.

An explicitly empty saved list deliberately removes that location's editable links. Restore default menu resets only the chosen location and advances its revision. Cart, account/login/join/sign-out controls, legal links, branding and the blue Cajun Web Pro new-tab credit remain outside editable menu data.

The owner guide is [Edit the public menus](../MENUS.md).

## Persistence and authorization

The feature uses the existing settings store: `navigation_menu_header` and `navigation_menu_footer`. File mode uses the protected file store; MySQL uses the existing settings table. **No new migration is required.** Each record has schema version 1, an integer revision, a configured flag and an ordered item tree. Absent locations use read-only defaults with revision zero. An explicit empty custom list is distinct from defaults. Reset stores a revisioned default-state record instead of deleting the setting, preventing an older pre-reset form from winning later.

Save and reset require POST, the Menus page/action/location contract, a valid CSRF token and a currently active saved owner. An owner role cached in a login session is insufficient. Every write rechecks saved ownership within the mutation boundary:

- File writes re-read under the existing common sidecar lock, apply only the selected location, and activate the resulting file atomically. Unrelated changes saved after an earlier read are retained.
- MySQL writes lock the current owner row and the unique setting row inside one transaction. The absent-setting insertion is confined to that transaction, so concurrent first saves are serialized. Revision comparison, setting update and audit insert commit together or roll back together.
- Audit entries record the action, location, resulting revision and item count. Invalid, unauthorized or stale attempts do not add a successful menu audit or partly commit settings.

Node validation rejects unsupported targets, duplicate/invalid identities, wrong field types, extra fields, invalid UTF-8, control characters, excess size/count/depth, destination-free leaves and unsafe URL schemes or paths. The posted JSON has a 262144-byte limit. Revisions are bounded to integers that also round-trip safely in JavaScript. Submitted edits fail as a whole rather than silently dropping offending nodes. Administrative responses use private/no-store caching.
