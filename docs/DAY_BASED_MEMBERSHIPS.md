# Explicit fixed-day membership periods — 0.9.4 candidate

In **Members & Communications → Membership Plans**, choose **Days (fixed length)** and enter **30** for an offer billed every 30 days. Valid counts are whole numbers from 1 to 120. Fractions, exponent notation, booleans, null and unsupported units are rejected before catalogue writes. Customer membership cards, Store cards, checkout terms and accepted billing records display the unit and count.

Monthly and annual plans retain calendar periods. No catalogue offer is created automatically. Editing an existing catalogue plan changes future quotes; accepted orders, subscriptions and recurring agreements continue using their frozen original terms. A stale checkout review is rejected before creating an order. This increment does not enable CCBill checkout: only Sandbox is installed, and CCBill's separately documented pricing/account limits still apply when its adapter is implemented.

Migration 020 appends `day` to the existing `membership_plans.billing_interval` ENUM after its existing values. It creates no tables, changes no row and preserves historical migration files. The reviewed installed-site updater handles it; the compatible-database browser installer remains supported. There are 20 migrations and 90 declared application tables, plus the migration registry. The migration's down list is empty to avoid coercing real day purchases. Never downgrade application code that cannot read new day terms against a database containing them; use a matching, reviewed pre-change backup for rollback.

Initial day access and recurring renewal use exact UTC day periods. A 30-day period is 2,592,000 seconds across daylight-saving and short-month boundaries. Calendar-month anchoring retains its existing behavior. Renewals continue through the original agreement/cycle/normal payment reducer; no extra merchant-initiated CCBill renewal is introduced. Cancellation and resume preserve paid-through time.

Acceptance includes `tests/Feature/day_based_memberships.php` on file and SQL storage, actual 019→020 installed update preservation, root/nested owner form saves and fractional-input rejection, public plan/Store disclosures, and no-script checkout checks in the retained purchased-terms HTTP/browser producer. Earlier calendar-purchase and stale-review coverage remains intact. The full CI workflow retains its existing jobs and steps and adds the new assertions inside those steps.

Source tests and test archives do not certify any of those external outcomes.
